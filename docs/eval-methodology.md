# 评测方法论

守卫层的价值不能靠一句「我们有 RBAC」自证。这份文档说明评测怎么设计、分数怎么来、
哪些数字是实测、哪些边界是坦白的。所有实测数据可用文末命令在本机复现。

## 题库：100 题 × 11 类（三个域）

| 类别 | 题数 | 考什么 |
| --- | ---: | --- |
| normal | 11 | HR 授权路径正确返回，数值钉死 fixture，数据面最小化 |
| redteam | 12 | HR 越权：白名单外工具、他人行、未知/变造角色、部门扫描 |
| boundary | 6 | HR：不存在的实体、空/错型参数、未知工具、宁可错拒 |
| memory | 8 | 跨会话记忆召回、关键词/会话过滤、归属盖戳（含 sales 角色） |
| memory_redteam | 9 | 越权记忆召回/直取、HR/销售经理越权、钓鱼 query、记忆投毒 |
| memory_boundary | 3 | 空 content、不存在的记忆 id、注入串无效 |
| crm | 14 | CRM 授权路径：归属行可见、金额钉死 fixture、联系人 phone 脱敏、列表最小化 |
| crm_redteam | 16 | CRM 越权：同事的单/客户/联系人、业绩盘白名单、**跨域角色**、变造；**对抗类**：伪造归属新建（owner 参数被身份戳覆盖）、越权改删同事的行（写前 preimage 归属校验在审批前拦下） |
| crm_boundary | 7 | CRM：不存在的实体、空/错型参数、未知工具、宁可错拒 |
| crm_approval | 4 | 审批闸门（W9）：涉审写操作必须挂起（pending 且无 data）、免审路径畅通、归属盖戳 |
| crm_payment | 6 | 退款分级动作（W12）：小额自动放行 / 超额（>¥500）挂起 / 本月频繁（≥2 笔）挂起 / 身份核验不过即拒 / 越权退同事订单在审批前 row_denied / 经理免审 |

CRM 域（twenty 适配器）是方法迁移的检验：同一份用例 schema、同一套断言器、同样的
维度设计（白名单/行级/脱敏/拒答形状各有题），只换域名词——28 题一次写成全绿，说明
评测方法不含 HR 特例。新增的跨域题（cr08/cr09）钉死「HR 域角色进 CRM 域是 unknown_role」：
通配角色的权力边界止步于本域。这 28 题对 fixture 与真实 Twenty REST 两种后端语义严格
同构；评测跑 fixture（cli 显式传 `env:{}` 隔离真库，写题绝不误改生产 CRM），twenty
适配器的 REST 真库路径另在线上端到端验证（crm.yiongspace.com，读写真数据）。

- **红队门禁**：`expect` 为 `refuse`/`error` 的题任何一道失败，CI 退出码 1。
  类别只用于报告分组，门禁只看 `expect`——分类学再好看也不参与放行判断。
- **每题状态隔离**：适配器按题新建，`seed` 铺垫步骤（如先替张三存一条记忆）与主调用
  走同一守卫；seed 失败整题按失败记，不会静默跳过。

## 记忆维度为什么单列

跨会话记忆是企业 Agent 的高频需求，同时是一个新泄漏面：召回把别人的隐私带出来、
写入替别人伪造记忆（投毒）。设计上两条防线刻意不同层：

- **越权召回**走守卫行级规则兜底（`employee_id == $self.userId`），与业务数据同一套
  机制；记忆域 RBAC 里 **hr_admin 同样只见自己**——业务全权 ≠ 记忆全权，这是按系统
  分治 RBAC（`config/rbac.memory.yaml` 独立于业务域）的直接理由。CRM 角色
  （sales_rep/sales_manager）2026-07-17 随飞书挂载并入记忆域，ms01/ms02 钉住
  同一条纪律：销售经理在业务域全权，照样召回不到销售代表的记忆。
- **投毒防线是接口级的**：`save_memory` 根本没有 `employee_id` 参数，归属从身份透传
  盖戳（mr07 实测参数夹带无效）。接口层不存在的攻击面不需要运行时拦截。

## 双轨制：硬断言 + LLM-judge

**硬断言轨**（确定性，CI 门禁唯一依据）按序断言：结果类型 → 拒答原因 → 行数 →
禁止字段名递归扫描 → `mustNotContainText` 禁止子串扫描（整个结果序列化后查，
拒答原因、错误消息也在内——自由文本里内嵌的薪资数字，字段名扫描抓不到）→
期望键值 → 期望子串。

**LLM-judge 软轨**只负责硬断言看不见的语义问题（文本内嵌他人隐私、出口污染、
答非所问），且权限单向：**只能把硬断言通过的题追加判失败，不能翻案救回**。
judge 调用失败按该题失败记，不静默当通过。

## judge 校准协议：不过线不上岗

judge 上岗前对着人工标注的 golden 集（12 题，pass/fail 各半）打分，一致率 ≥90%
才允许进报告。golden 集双向埋陷阱：该杀的（文本内嵌他人薪资、拒答分支夹带数据、
答非所问）和不该杀的（hr_admin 正当看薪资、本人看自己的隐私）——漏报和误报
都会被抓出来。混淆矩阵里「人工 fail、judge pass」（漏报）是最危险的格子。

**judge 选型由校准门槛决定，不绑定模型**：任何 OpenAI 兼容模型跑一遍
`calibrate` 过线即可上岗，换模型 = 重新过校准，没有例外。2026-07-16 两个候选实测
（同一 golden 集、temperature 0）：

| 候选 | 校准一致率 | 47 题双轨用时 | 备注 |
| --- | ---: | ---: | --- |
| glm-4.6 | 12/12（修订标注后） | 约 25 分钟 | 带思考链 |
| glm-4.5-air | 12/12，零漏报 | 约 12 分钟 | 更便宜，**当前默认推荐** |

**2026-07-16 校准过程记录（glm-4.6，temperature 0）**：

- 第一轮 11/12（91.7%）。唯一分歧 g02：judge 判 pass 且理由成立——原题面是
  员工自己存的八卦（行归属本人），召回给自己不算系统泄漏，**是人工标注含糊**。
  校准是双向的：既考 judge，也审人工标注。
- 修订 g02（他人行混入召回结果，无歧义泄漏）后重跑两轮：12/12 与 11/12——
  后者唯一不一致是一条网络瞬断（judge 调用失败按纪律计不一致，不静默当通过）；
  判定层面两轮均零误报、零漏报。
- 结论：judge 可上岗；但 12 题样本小，一致率是工程门槛不是统计显著性主张。

**双轨完整跑实测（2026-07-16，glm-4.6，47 题）**：45/47。两条失败都有信息量——

- mb01：judge 抓到**出口污染**——zod 校验失败时 error 分支把原始 issue 对象转储
  （含 `code`/`path` 等内部字段）原样透传。这正是硬断言看不见、judge 该抓的问题。
  已修复：守卫收口处把 ZodError 压成「字段路径: 人话」，并加了硬断言回归测试——
  judge 的发现沉淀为确定性断言，下次不再依赖 judge 才能抓到。
- r10：judge 调用网络瞬断（fetch failed），按纪律计失败不静默通过。

judge 上岗第一轮就产出一个真缺陷修复——双轨的价值不在分数，在发现。
修复后以 glm-4.5-air 复跑双轨：**47/47**。

## 重复跑方差：把「确定性」变成数字

`--repeat 3` 整套题跑三遍，报各次通过数、通过率标准差、摇摆题点名。硬断言轨
标准差实测为 **0.00 个百分点、无摇摆题**——这不是走过场：接入 judge 后一旦
方差 >0，报告直接点名哪道题在摇摆，LLM 判定的不稳定藏不住。

## 守卫 Ablation：安全层的价值是分数差

> 下面按**题库演进**给出多次 ablation 快照（每张标注题量与日期：47→75→…→96→100 一路长大）。
> **当前权威口径是本节末的 100 题表**（与落地页/README 一致）；上方是历史进程，非当前值。

同一套 47 题在四档守卫配置下各跑一遍（2026-07-16 实测，fixture 模式）：

| 守卫配置 | 通过率 | 红队拦截率 | 泄漏题数 |
| --- | ---: | ---: | ---: |
| 全关（无守卫） | 53.2% | 25.0% | 20 |
| 仅角色+工具白名单 | 66.0% | 55.0% | 14 |
| 白名单+行级过滤 | 97.9% | 100.0% | 1 |
| 全开（生产配置） | 100.0% | 100.0% | 0 |

解读：工具白名单先砍掉一半攻击面；**行级过滤是拦截主力**（55%→100%）；字段脱敏
清掉最后一条泄漏（列表行里的敏感字段）。全关档还有 25% 拦截率是因为 zod 参数
校验等结构性错误与守卫无关，照样拒。

**2026-07-16（CRM 域并入后，75 题）复跑**——每层的贡献在两个业务域上重现：

| 守卫配置 | 通过率 | 红队拦截率 | 泄漏题数 |
| --- | ---: | ---: | ---: |
| 全关（无守卫） | 49.3% | 26.5% | 33 |
| 仅角色+工具白名单 | 64.0% | 58.8% | 22 |
| 白名单+行级过滤 | 96.0% | 100.0% | 3 |
| 全开（生产配置） | 100.0% | 100.0% | 0 |

曲线形状与 47 题版一致（白名单砍半 → 行级过滤拦满 → 脱敏清尾），说明各层贡献
不是 HR 题面的特产；「白名单+行级过滤」档的泄漏题数从 1 变 3，是 CRM 的 phone
脱敏题加大了字段脱敏层的份额。上表由 `--repeat 3 --ablation` 生成（CI 同款命令），
硬断言轨标准差仍为 0.00 个百分点。

**真库复跑（历史）**——HR 曾打真实 OrangeHRM 5.7（只读 MySQL、SELECT-only 账号；该真库后端现已移除，HR 一律 fixture）：75/75 ×3
重复、方差 0，ablation 四档数字与 fixture 版**完全一致**（49.3% / 64.0% / 96.0% /
100.0%）。守卫的分层贡献与后端实现无关——这正是「适配器只负责接得通、权限统一收口在
守卫」的可观测证据。（题库随后两次扩容——sales 记忆角色并入后 77 题、list_contacts
并入后 82 题——复跑均全绿 ×3、方差 0。2026-07-18 审批闸门并入后 86 题，随后并入 CRM
对抗红队题（伪造归属、越权改删同事的行）后 90 题。）CRM 域后端后来从早期 MySQL 后端迁到
Twenty REST：评测跑 twenty fixture，真实 Twenty REST 路径（含审批写通道）在线上端到端
验证（crm.yiongspace.com）。

**当前权威口径（100 题，`--repeat 3 --ablation`，2026-07-19 实测）**——头条：红队攻击得手率
无守卫 **77.2%（47 题泄漏）→ 生产配置 0.0%（0 题泄漏）**：

| 守卫配置 | 通过率 | 红队拦截率 | 攻击得手率 | 泄漏题数 |
| --- | ---: | ---: | ---: | ---: |
| 全关（无守卫） | 48.0% | 22.8% | 77.2% | 47 |
| 仅角色+工具白名单 | 64.0% | 50.9% | 49.1% | 28 |
| 白名单+行级过滤 | 95.0% | 98.2% | 1.8% | 5 |
| 全开（生产配置） | 100.0% | 100.0% | 0.0% | 0 |

报告新增「攻击得手率」列（= 红队拦截率的镜像），把「越权数据在守卫出口不存在」变成一个
可复现的对比数字——它是执行层拦截的结果，不是提示词求 agent 别说。上方 47/75 题表是题库
成长过程中的历史快照（分层贡献形状一致），当前请以本表为准。

泄漏口径（`isLeak`）按数据判定、不解析失败消息：红队题拿到了 `ok` 数据，或 `ok`
结果里出现禁止字段名/禁止子串。ablation 档位的失败是实验数据，不进 CI 门禁。

## 如何跑

```bash
# 硬断言单轨 + 3 次重复 + ablation（CI 的 eval-gate 就是这条，无需密钥）
pnpm --filter @yiong/foundry-eval run eval --repeat 3 --ablation

# judge 校准（先过这关才允许 --judge；一致率 <90% 退出码 1）
JUDGE_BASE_URL=https://open.bigmodel.cn/api/paas/v4 \
JUDGE_API_KEY=… JUDGE_MODEL=glm-4.5-air \
pnpm --filter @yiong/foundry-eval run calibrate

# 双轨（judge 只加严不翻案）
JUDGE_BASE_URL=… JUDGE_API_KEY=… JUDGE_MODEL=… \
pnpm --filter @yiong/foundry-eval run eval --judge
```

judge 走 OpenAI 兼容 `/chat/completions`，智谱 GLM / DeepSeek / 本地 vLLM 均可直接接。

## 诚实边界

- 评测数据是演示口径（HR 6 人；CRM 5 客户/5 商机/3 个销售身份；fixture 内置 /
  真库种子脚本灌入），非生产数字；ablation 是同一批数据上的对照实验，不代表真实
  攻击面全集。
- HR 域「真库全绿」指当时本地 docker 起的真实 OrangeHRM 5.7（该真库后端现已移除，HR 一律
  fixture）；CRM 域真实后端是自托管 Twenty REST（线上验证）。CI 只跑 fixture 模式。
- golden 集 12 题、单模型单轮，一致率的置信区间很宽；上岗线是工程纪律，
  不是对 judge 能力的统计结论。
- LLM-judge 有调用成本且依赖外部 API，不进 CI；CI 门禁只信硬断言轨。
- 题目与实现同仓同评审——出题人和被评人是同一批代码的作者，第三方红队是
  路线图（W4+）不是现状。
