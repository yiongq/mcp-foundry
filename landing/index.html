为什么做

三个事故 → 三个能力

安全不靠提示词自觉——结构化规则在守卫层强制执行。

事故:员工顺嘴一问,拿到同事工资

角色 → 工具白名单

不该用的工具在 tools/list 里根本不出现,而不是调用被拒后再解释。

事故:模型把手机号、薪资整行吐进回答

行级过滤 + 字段脱敏

结构化规则在守卫出口强制执行;越权数据不进上下文,模型想编也没材料。

事故:出事后翻不出谁问过什么

逐调用审计流水

每次调用一条 JSONL;只记参数哈希不记原文,审计日志不成为第二个泄漏面。

人工审批 · Human-in-the-loop

动钱、改库这类高危写,先过人的点头

行级过滤拦得住泄漏,拦不住已经发生的写。涉审写操作在执行前被挂起成审批单,独立审批人批准后才落库——审批必须在写入之前。

Guard 管线 · 审批闸门在 execute 之前
1角色查找 → 工具白名单
2写前归属校验(preimage)越权即 row_denied
3审批闸门pending · 无 data
4adapter.execute(人批准后)一单一次
5行级过滤 → 字段脱敏 → 审计
01
独立审批人,不能自批
发起人(sales_rep)与审批人(sales_manager,approver:true)分离;RBAC 只标谁能批(approver:true),而「发起人不能批自己的单」是网关代码级硬校验(userId 比对)。
02
闸门在写入之前
挂起发生在 adapter.execute 之前——行级过滤拦得住读的泄漏,拦不住已经落库的写。审批必须在写入发生前。
03
一单一次,防重放
批准后同参调用重试即消票执行;审批单一次性核销,重复提交不再触发第二次写入。
04
拒答/挂起分支无 data
pending 与 refusal 在类型层就没有 data 字段,结构上不可能夹带业务数据或模型自由文本。

why

Three incidents → three capabilities

Safety doesn't rely on prompt discipline — structured rules are enforced at the guard layer.

Incident: a casual question returns a coworker's salary

Role → tool whitelist

Off-limits tools never appear in tools/list — instead of rejecting the call and explaining afterwards.

Incident: the model dumps whole rows — phones, salaries — into answers

Row filtering + field masking

Enforced at the guard's exit; unauthorized data never enters the context, so there's nothing to leak.

Incident: afterwards, no one can tell who asked what, when

Per-call audit trail

One JSONL line per call; params stored as hashes, never raw — the audit log doesn't become a second leak surface.

Human-in-the-loop

Money and mutations wait for a human's nod

Row filtering stops leaks, not writes that already happened. Approval-gated writes are suspended as a ticket before execution; only an independent approver's sign-off commits them — approval must precede the write.

01
Independent approver, no self-approve
The requester (sales_rep) and approver (sales_manager, approver:true) are separate; RBAC only marks who may approve (approver:true); the no-self-approve rule itself is a hardcoded gateway check (userId comparison).
02
The gate sits before the write
Suspension happens before adapter.execute — row filtering stops read leaks, not writes already committed. Approval must precede the write.
03
One ticket, once — replay-safe
After approval, retrying the same call consumes the ticket and executes; the ticket is single-use, so resubmits never fire a second write.
04
Refusal/pending carry no data
pending and refusal branches have no data field at the type level — structurally incapable of smuggling business data or model free-text.

What was verified — and what wasn't

Overpromising is the worst failure mode for a security product. These limits stay in sync with the README:

✓both real backends verified: HR against real OrangeHRM 5.7 (read-only MySQL, local docker; docker retired, prod runs fixture), CRM against real Twenty (REST + Bearer, live) — demo-scale data, not production scale
✓The live CRM domain runs real Twenty (crm.yiongspace.com reads/writes real data); the HR domain stays on fixture online
✓Demo identities are pre-configured, not logged in — it demonstrates "same gateway, different identity, different behavior", not a login system
✓Row/field rules apply only at the guard's exit; bypassing Foundry to hit the source system directly is out of scope — source credentials go to Foundry only
✓JWKS URL mode defaults to availability-first: during a prolonged endpoint outage revocation doesn't take effect; fail-closed requires opting into max-stale
✓ERP is still roadmap; "multi-issuer" is a capability — the live deployment is single-issuer
